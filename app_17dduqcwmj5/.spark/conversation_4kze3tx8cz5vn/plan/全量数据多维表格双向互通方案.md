# 全量数据多维表格双向互通方案

## 1. 目标与成功标准

- 应用内 9 类数据（课程、课程类别、FAQ知识库、未命中问题、营销内容、素材库、器材工具、工艺流程、配方明细）全部与多维表格双向互通：应用内增/改/删实时回写多维表格；多维表格侧改动经已有/新建同步任务回灌应用
- 每条记录有同步状态（已同步/失败/未同步）可见，失败可一键重试，回写失败不影响本地操作（沿用学员/排期/考勤已验证的 `server/src/common/bitable-sync/` 架构）
- 3 张多维表格中不存在的表（营销内容、课程类别、未命中问题）由用户按给定字段定义手动建表后接入

## 2. 关键实现文件

- `server/src/common/bitable-sync/bitable-sync.constants.ts` — 新增 9 个插件实例 ID 常量
- `server/src/common/bitable-sync/bitable-sync.mapper.ts` — 新增 9 种 recordType 的 DB 行→多维表格字段快照映射
- `server/src/common/bitable-sync/bitable-sync.service.ts` — loadSnapshot/markSynced/markFailed/删除分支扩展 9 张表
- `shared/bitable-sync.ts` — `BitableRecordType` 扩展 9 个类型
- `server/modules/course/course.service.ts` + `course.controller.ts` — 课程/类别写路径挂回写；新增器材/流程/配方写端点
- `server/modules/consultation/consultation.service.ts` + controller — FAQ/未命中问题写路径挂回写
- `server/modules/content/content.service.ts` + controller — 营销内容写路径挂回写；新增素材库写端点
- `server/database/schema.ts` — DDL 后 codegen 自动重新生成
- 前端：`pages/courses/*`、`pages/consultation/*`、`pages/content-center/*` — 同步状态列 + 重试按钮 + Group C 编辑弹窗

## 3. 实现方案

### 3.1 数据分组与互通方式（统一复用现有回写架构）
- Group A（多维表格已有表、应用可编辑）：课程总表、FAQ知识库 → 仅挂回写
- Group B（多维表格无表、应用可编辑）：营销内容、课程类别、未命中问题 → 用户手动建表 → 建同步任务 + 挂回写
- Group C（多维表格已有表、应用当前只读）：素材库、器材工具、工艺流程、配方明细 → 新增应用内编辑能力 + 挂回写

### 3.2 双向一致性规则（沿用学员/排期/考勤已验证模式）
- 回写成功后将返回的 Base record id 同时写入 `bitable_record_id` 与 `base_record_id`，确保 streaming 同步任务回灌时命中同一行、不产生重复记录
- 应用内删除记录时调用插件 `deleteRecords` 同步删除多维表格行；插件实例需配置 `batchAddRecords` + `batchUpdateRecords` + `deleteRecords` 三个 action
- 时间字段转时间戳、数字字段转 Number、关联字段传字符串数组（record id 数组），严格按已有 mapper 的既有转换规则

## 4. 具体步骤

### 步骤1：数据库扩展（9 张表加同步字段）
- `+db-execute` 为 9 张表执行 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS bitable_record_id varchar(255), ADD COLUMN IF NOT EXISTS sync_status varchar(32) NOT NULL DEFAULT 'not_synced'`（执行前向用户展示影响并确认）
- 执行 `code_gen database_schema` 后重新读取 `schema.ts`
- 预期：9 张表具备同步状态字段

### 步骤2：新建表字段定义交付 + 用户手动建表（外部依赖，尽早发起）
- 从 `shared/api.interface.ts` 与前端常量读取真实枚举值，输出 3 张表的字段定义清单交用户建表：
  - 「营销内容」：标题(文本)、内容类型(单选，按应用现有枚举)、正文内容(多行文本)、状态(单选，按应用现有枚举)、计划发布日期(日期)、拒绝原因(多行文本)、发布平台(文本)、点赞数(数字)、转化数(数字)、关联课程(文本)
  - 「课程类别」：类别名称(文本)
  - 「未命中问题」：问题(多行文本)、状态(单选：待处理/已转化，按应用现有值)
- 用户建好后回填 3 张表的 Base 链接；随后用 `+db-sync-create --preview` → 确认后 `--yes` 各建一个 Base→DB streaming 同步任务（显式 `--environment` 按 db-sync 规则，单环境应用省略）
- 预期：3 张新表具备 Base→应用 同步通道

### 步骤3：创建 9 个回写插件实例
- 每张表一个实例（命名 `bitable_<table>_sync`），经 `plugin_instance` CREATE，selectedPluginKey 为 feishu-bitable
- requirementsSummary 必须逐一列出目标表全部字段名/类型/选项（插件实例 formValue.fields 为空会静默丢字段，见项目记忆），并要求配置 batchAddRecords/batchUpdateRecords/deleteRecords
- 创建后检查 `capabilities/<id>.json` 的 formValue.fields 非空；将实例 ID 写入 `bitable-sync.constants.ts`
- Group B 的 3 个实例在步骤2 用户回填链接后创建
- 预期：9 个可真实调用的回写通道

### 步骤4：回写基础设施扩展
- `shared/bitable-sync.ts` 扩 `BitableRecordType`；constants 加 9 个插件 ID
- mapper 增加 9 种快照映射：字段中文名以各表 `+db-sync-get` 返回的 field_maps 中 base_field.name 为准（已有表先读取校准，禁止凭猜测写字段名）
- service 的 loadSnapshot/markSynced/markFailed 支持 9 张表；新增删除分支调用 deleteRecords
- 预期：`syncRecord(recordType, id)` 支持全部 12 种类型

### 步骤5：Group A/B 写路径挂回写 + 通用重试
- 课程：`POST api/courses`、`PATCH api/courses/:id` 成功后 `syncRecord('course', id)`；类别 `POST/DELETE api/courses/categories` 挂回写/删除回写
- 咨询：`POST/PATCH api/faqs`、`POST api/faq-misses/:id/convert` 及未命中问题 insert 处挂回写
- 营销内容：创建 + 审核/使用/素材/效果 4 个 PATCH 挂回写
- 新增通用重试端点 `POST api/bitable-sync/retry`（body: recordType + recordId，@NeedLogin）
- 前端：课程列表、类别弹窗、FAQ 面板、未命中面板、内容管理列表增加同步状态列 + 重试按钮（复用学员列表的样式与交互模式）
- 预期：上述任何写操作后多维表格出现/更新对应行，失败可重试

### 步骤6：Group C 应用内编辑能力 + 回写
- 后端：素材库（素材标题/类型/关联课程/核心内容/适用平台/标签/状态）、器材工具（名称/规格/数量/备注/所属课程）、工艺流程（步骤号/名称/操作说明/关键控制点/预计时长/所属课程）、配方明细（原料名/用量/单位/分类/备注/所属课程）各新增 create/update/delete service 方法与端点，成功后挂回写
- 前端：素材库 Tab 新增「新增素材」与编辑/删除操作；课程详情页配方、工艺流程、器材三个 Section 增加新增/编辑/删除入口与表单 Dialog（遵循 forms-skill，shadcn 组件）
- 预期：4 类数据可在应用内维护并双向同步

### 步骤7：验收
- 用 `api_request` 对每类数据的写接口以 `[API_TEST]` 数据做写入→读回→重试校验；删除类仅清理本轮测试数据；确认服务端日志无插件调用报错
- 前端走查同步状态列与重试按钮；清理或声明残留测试数据

## 5. 影响范围与风险

- 双向同步固有风险：多维表格侧修改会经 streaming 任务覆盖应用内数据（与学员/排期/考勤现状一致，可接受）
- 已有表字段名映射错误会导致回写静默失败——以 `+db-sync-get` 的 field_maps 为唯一字段名来源
- Group C 开放编辑后，多维表格侧同样可改这些表，冲突按"后写覆盖"处理
- 9 张同步表加列不改变已有字段，streaming 任务不受影响；`bitable_record_id`/`base_record_id` 双写防止回灌重复行

## 6. 验收标准

- 12 类数据（原 3 + 新 9）在应用内创建/编辑后，多维表格对应表出现/更新记录，状态列显示"已同步"
- 模拟回写失败（如停插件）时本地写入不受影响，状态显示"失败"，点击重试后恢复"已同步"
- 课程类别删除后多维表格对应行被删除
- Group C 四类数据可在应用内新增/编辑/删除，且同步到多维表格
- 3 张新建表在用户建表并回填链接后，双向通道可用（Base→应用同步 + 应用→Base 回写）
- 全部写接口 `[API_TEST]` 验证通过，服务端运行日志无报错

## 7. 未决事项

- 3 张新表的实际创建与 Base 链接回填依赖用户操作；用户回填前，步骤2 后半段、步骤3 的 3 个实例及 Group B 的联调需挂起，其余步骤可先行
