# 角色成员无权限排查与修复

## 目标与成功标准
- 李奇华（已被添加为校长/管理员）打开应用后，左侧菜单按 principal 角色完整显示（含权限管理），进入各页面不再跳 /unauthorized
- 任何登录用户的菜单/路由权限判断与后端 @CanRole 鉴权同源，不再依赖经常 404 的平台 `__runtime__` 权限接口
- 成功标准：`POST /api/auth/my-roles` 返回当前用户 roleList（含 principal）；李奇华重开应用菜单恢复、可进权限管理页

## 根因（已验证事实）
1. 平台数据正常：`+role-member-list principal` 含李奇华 `ou_7507...705ea`；`+role-match-list` 对李奇华返回命中 principal；可见范围 Tenant 全员
2. 前端 ability 来源失效：client-toolkit 的 AuthProvider 默认请求 `/app/<appId>/__runtime__/api/v1/permissions/roles`，实测 dev 网关 404（curl 验证，旧路径 `/spark/...` 同样 404）→ ability 恒空 → `CanRole`/`ProtectedRoute`（client/src/components/ProtectedRoute.tsx:38、client/src/components/Layout.tsx:172）全判 false → 菜单只剩未受控项（/consultation /courses /schedules，恰为学员可见菜单），每页跳 /unauthorized。owner 视角因平台豁免不受影响，故只有对方复现
3. SDK 预留注入口：`@lark-apaas/auth-sdk` 的 AuthProvider 支持 `config.permissionApi`（permission-client.js:16-28：POST 该 url，解析 `data.data?.roleList`）；client-toolkit/auth 已 re-export AuthProvider，与页面使用的 CanRole 同 Context 实例，内层 Provider 可覆盖外层

## 关键实现文件
- `shared/api.interface.ts`：新增 `MyRolesResponse = { data: { roleList: string[] } }`
- `server/modules/auth/auth.controller.ts` + `auth.module.ts`（新建）：`@NeedLogin() @Post('my-roles')` 返回 `{ data: { roleList: req.userContext?.roles ?? [] } }`
- `server/app.module.ts`：注册 AuthModule（ViewModule 之前）
- `client/src/app.tsx`：模块级 `const AUTH_SDK_CONFIG = { permissionApi: { url: '/api/auth/my-roles' }, enable: true }`；`<Routes>` 外层包 `<AuthProvider config={AUTH_SDK_CONFIG}>`（从 `@lark-apaas/client-toolkit/auth` 导入）

## 实现方案
- 后端角色源用 `req.userContext.roles`（fullstack-nestjs-core 类型注释 `roles?: string[]`，与后端 @CanRole 同源），值为角色 bizID（principal 等，与 shared/roles.ts APP_ROLES 一致）
- 前端不新增 api 函数：SDK PermissionClient 自行 fetch 该 url；响应必须形如 `{ data: { roleList: [...] } }`
- config 必须是模块级 const（AuthProvider.js:43-52 的 useCallback/useEffect 依赖 config 引用，内联对象会触发重复拉取死循环）
- ProtectedRoute / Layout / 各页面 CanRole 全部不改（读最近 Context，自动切到新 Provider）
- 未登录：my-roles 401/空 → ability 空，ProtectedRoute 现有 loginState==='anonymous' 分支优先显示 LoginPrompt，行为不变

## 具体步骤
1. shared/api.interface.ts 追加 MyRolesResponse
2. 新建 server/modules/auth/：controller（POST api/auth/my-roles，@NeedLogin，读 req.userContext.roles）+ module；app.module.ts 注册
3. client/src/app.tsx 包 AuthProvider（模块级 const config）
4. 自测：api_request POST /api/auth/my-roles（auth 模式）→ 200 且 roleList 含 principal；anon 模式 → 401 或空 list 均可
5. 读 server-devserver/trace 日志确认无运行时报错；提交代码

## 影响范围与风险
- 仅新增一个后端接口 + app.tsx 包一层 Provider；不改任何现有鉴权使用点与角色数据
- 风险1：`req.userContext.roles` 若运行时为空数组（平台未注入），自测即暴露；兜底改法：controller 内 roles 为空时返回 401 触发前端 error 态（仍走 LoginPrompt/Unauthorized 现有分支），并回退调研 authz-guide 的服务端查询 API
- 风险2：SDK 并发请求 `user-points` 端点 404 —— Promise.allSettled 容忍（AuthProvider.js:21-27），无影响
- 外层 AppContainer 的默认 AuthProvider 仍会 404 一次，仅多一次无效请求，无副作用

## 验收标准
- `POST /api/auth/my-roles`（auth）→ 200，`data.roleList` 含 `principal`
- 预览页以登录态打开：菜单完整（含权限管理），/permissions 可进入不跳 unauthorized
- 请李奇华重开应用链接：菜单按校长角色显示、各页面可进入（用户侧验收）
- 游客视角：仍显示 LoginPrompt，不卡 loading

## 未决事项
- `req.userContext.roles` 的实际运行时内容以步骤 4 自测结果为准；若与 bizID 不一致需按兜底改法调整（不影响方案主线）
