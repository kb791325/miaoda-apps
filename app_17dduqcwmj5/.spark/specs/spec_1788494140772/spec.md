# 需求分析
## 用户故事
1. 应用内新增学员自动回写多维表格
  - 1.1 通过「新增学员」提交报名登记后，本地学员表写入成功，同时该学员信息被写入飞书多维表格的学员表
  - 1.2 回写成功后多维表格中出现对应记录，且本地保存多维表格记录标识，后续不会被重复创建
  - 1.3 回写失败时本地学员数据不受影响，前端给出「同步多维表格失败」提示
  - 1.4 对学员信息编辑或录入缴费后，多维表格中对应记录同步更新为新值

2. 应用内新增排期自动回写多维表格
  - 2.1 「新增排期」提交成功后，排期信息（排期名称、课程、上课日期、起止时间、讲师、教室、招生容量、状态）写入多维表格排期数据表
  - 2.2 回写成功后本地保存多维表格记录标识；回写失败不阻塞本地创建并提示

3. 应用内考勤标记自动回写多维表格
  - 3.1 在考勤抽屉逐人标记考勤状态并保存后，每条考勤记录写入多维表格考勤数据表（学员、所属排期、考勤状态、备注）
  - 3.2 再次修改同一场次考勤并保存时，多维表格中已有记录被更新而非重复新增
  - 3.3 回写失败时本地考勤保存不受影响并给出提示

4. 查看数据同步状态并支持失败重试
  - 4.1 学员列表、排期列表每行展示同步状态标识（已同步 / 同步失败）
  - 4.2 同步失败的行提供「重新同步」操作，点击后再次回写多维表格，成功后标识更新为已同步
  - 4.3 多维表格未配置时不展示同步失败轰炸，给出「未配置多维表格」的统一说明

## 页面列表
### 学员管理页（既有页面扩展）
1. 列表行新增多维表格同步状态标识列（已同步/失败/未同步）
2. 同步失败行提供「重新同步」操作，成功后提示并刷新标识
3. 「新增学员」「编辑」「录入缴费」提交后自动触发回写，失败给出非阻塞提示

### 课程排期页（既有页面扩展）
1. 排期列表行新增同步状态标识，失败行提供「重新同步」
2. 「新增排期」提交后自动触发回写，回写失败不阻塞本地创建

### 考勤抽屉（既有组件扩展）
1. 考勤保存成功后自动回写多维表格考勤数据表，失败时保留本地结果并提示

# 技术方案
## 开发元信息
- 开发模式: 全栈应用
- 涉及层级: [数据库, 插件, 服务端, 前端]
- 现状说明：课程、学员、排期、考勤、素材、FAQ 等表已是「多维表格 → 本地库」单向同步表（含 base_record_id 字段与平台自动同步机制），本次补齐「应用内写入 → 多维表格」反向回写，实现双向互通；同步表禁止通过插件做删除操作，避免与平台同步机制冲突
## 页面路由与导航
### 导航设计
- 导航机制：页面路由
- 导航项：沿用现有左侧导航，不新增页面与导航项；同步状态与重试操作挂载在学员管理页、课程排期页既有列表及考勤抽屉内
## 数据模型
### 数据库设计
既有表扩展（仅新增字段，不改表名字段名）：

#### 学员表（student_registration_table）扩展
用途：记录学员记录在多维表格中的回写映射与同步状态。
新增字段：
- bitable_record_id: varchar（该学员在多维表格学员数据表中的记录 ID，回写成功后写入，用于后续更新定位）
- sync_status: varchar ['synced', 'failed', 'not_synced']，默认 'not_synced'（回写多维表格的同步状态）

#### 排期表（course_schedule_table）扩展
用途：记录排期记录在多维表格中的回写映射与同步状态。
新增字段：
- bitable_record_id: varchar（多维表格排期数据表记录 ID）
- sync_status: varchar ['synced', 'failed', 'not_synced']，默认 'not_synced'

#### 考勤表（attendance_record_table）扩展
用途：记录考勤记录在多维表格中的回写映射与同步状态。
新增字段：
- bitable_record_id: varchar（多维表格考勤数据表记录 ID）
- sync_status: varchar ['synced', 'failed', 'not_synced']，默认 'not_synced'

映射与写入规则：
- 本地记录无 bitable_record_id 时，回写走「新增记录」并把返回的记录 ID 写回该字段；已有 bitable_record_id 时，回写走「更新记录」
- 从多维表格同步下来的存量记录已有 base_record_id，其 bitable_record_id 初始置为与 base_record_id 一致并标记已同步，避免重复创建
## 插件设计
多维表格回写统一在服务端 Service 内调用（结果需落库、属于强数据一致性链路），通过 CapabilityService 调用。目标多维表格的 appToken 与三张数据表的 tableID 由用户提供；执行阶段通过配置表或环境变量读取，禁止硬编码。

| 插件名称 | 基础插件 | 用途 | 调用方式 | 关联页面 | 输入参数 | 输出类型 |
|---------|---------|------|---------|---------|---------|---------|
| bitable-record-add | feishu-bitable | 向指定数据表批量新增记录（batchAddRecords） | 服务端 CapabilityService | 学员管理、课程排期、考勤抽屉 | 数据表标识、记录字段键值对 | 新增记录 ID 列表 |
| bitable-record-update | feishu-bitable | 向指定数据表批量更新记录（batchUpdateRecords） | 服务端 CapabilityService | 学员管理、课程排期、考勤抽屉 | 数据表标识、记录 ID 与字段键值对 | 更新结果 |

说明：
- 按插件原子化要求将「新增」与「更新」拆为两个实例；目标数据表标识（学员表/排期表/考勤表）经 input 动态传入，两个实例即可覆盖三张数据表的回写
- 若执行阶段发现实例已存在可复用则直接复用，不重复创建
- 回写字段按多维表格字段名组织：学员表（姓名、联系电话、微信号、来源渠道、报名日期、缴费状态、缴费金额、学习进度、结业日期、备注）；排期表（排期名称、课程名称、上课日期、起止时间、讲师、教室、招生容量、状态）；考勤表（学员、课程排期、考勤状态、备注）
## 业务模型
### API 设计
#### 学员管理页 相关
**页面路径**: /students
**功能全景**：
| 功能 | 实现方式 | 说明 |
|------|----------|------|
| 新增学员回写多维表格 | 插件（服务端调用） | 既有创建学员 Service 落库成功后调用 bitable-record-add，写回记录 ID 与同步状态 |
| 编辑学员/录入缴费后更新多维表格 | 插件（服务端调用） | 既有 PATCH /api/students/:id 与缴费接口落库后调用 bitable-record-update |
| 列表展示同步状态 | API | 既有学员列表接口响应扩展 syncStatus 字段 |
| 失败重试 | API + 插件 | 新增重试接口，按记录类型重新回写 |

**所需 API**:
```typescript
// 学员列表响应扩展（在既有 GET /api/students 响应项中新增字段） [领域模型: StudentModel] [对应页面功能: 同步状态标识]
Response 每项新增: { bitableRecordId?: string; syncStatus: 'synced' | 'failed' | 'not_synced' }

// 学员同步重试 [领域模型: StudentModel] [对应页面功能: 重新同步]
POST /api/students/:id/bitable-sync
Response: { syncStatus: 'synced' | 'failed'; message?: string }
```

#### 考勤抽屉 相关
**挂载位置**: 课程排期页考勤抽屉
**功能全景**：
| 功能 | 实现方式 | 说明 |
|------|----------|------|
| 考勤保存后回写多维表格 | 插件（服务端调用） | 既有考勤保存接口落库后，按记录有无 bitable_record_id 分别调用新增/更新实例 |
| 考勤保存结果提示扩展 | 前端 | 回写失败时本地结果保留并提示同步失败 |

#### 通用同步服务（服务端内部，不暴露为独立页面）
- 封装统一的 BitableSyncService：读取多维表格配置（appToken/tableID）→ 组装字段映射 → 调用对应插件实例 → 回写 bitable_record_id 与 sync_status
- 回写采用「本地落库成功优先」策略：本地事务提交后异步/顺序触发回写，回写失败仅标记 failed，不回滚本地数据
- 多维表格未配置时跳过回写并标记 not_synced，前端展示「未配置多维表格」提示而非失败告警
