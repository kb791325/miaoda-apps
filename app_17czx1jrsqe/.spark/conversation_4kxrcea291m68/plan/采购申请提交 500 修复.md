# 采购申请提交 500 修复方案

## 目标与成功标准
- 用户在采购申请页提交新建/编辑申请时不再报 500
- 物品明细（对象数组）能正常落库并在列表/编辑时正确回读
- 如遇 Bitable 字段错误，返回明确的中文错误提示而非裸 500

## 根因（已验证）
- `采购明细`字段在 Bitable 是文本类型，`toBitableValue` 对 `[{name,spec,quantity,...}]` 对象数组原样透传 → Bitable 报字段类型错误（1254061 类）
- `bitable.entity.service.ts` create/update 未捕获 `bitable.request` 抛出的 Error → Nest 全局过滤器兜成 500
- 前端连续 2 次失败触发 mock 降级 → mock 无该 POST 路由 → 显示「后端暂不可用」

## 关键实现文件
- `server/config/feishu.config.ts` — 新增 `JSON_TEXT_FIELDS` 配置清单（采购-采购申请.采购明细、采购-采购订单.订单明细、采购-采购详情.详情明细）
- `server/common/feishu/field-normalizer.ts` — `toBitableValue` 写入侧 JSON.stringify；`normalizeRecord` 读取侧 JSON.parse
- `server/modules/bitable/bitable.entity.service.ts` — create/update/batchCreate/batchUpdate 捕获 Bitable Error 并转为 BadRequestException，附带错误码与中文描述
- `client/src/pages/Admin/PurchaseReqPage.tsx`（或对应页面文件）— `safeItems` 兼容 JSON 字符串回读
- `client/src/pages/Admin/PurchaseFormDialog.tsx` — 提交格式保持不变（数组），无需改动

## 实现方案

### 1. JSON 文本字段配置（feishu.config.ts）
- 新增 `JSON_TEXT_FIELDS: Record<string, string[]>`，以 tableKey 为键，字段中文名为值
- 第一批覆盖：`采购-采购申请: ['采购明细']`、`采购-采购订单: ['订单明细']`、`采购-采购详情: ['详情明细']`
- 字段类型未知的表不加入，避免误序列化

### 2. 写入/读取双向转换（field-normalizer.ts）
- `toBitableValue(fieldName, value, tableKey?)` 末尾增加：若 `tableKey` 在 `JSON_TEXT_FIELDS` 中且 `fieldName` 属于该表清单，且 value 为对象/数组 → `JSON.stringify(value)`；空数组 → `'[]'`；null/undefined → null
- `normalizeRecord(record, tableKey)` 末尾增加：对同清单字段，值为非空字符串时 `try JSON.parse`，失败保留原字符串（不中断正常展示）

### 3. 服务端错误捕获（bitable.entity.service.ts）
- create / update / batchCreate / batchUpdate 四处包 `try/catch`
- 捕获到 Bitable Error（含 `Bitable API error code=`）时：提取 code 和 msg，映射常见错误码到中文描述（1254061=字段类型不匹配、1254069=附件格式错误、1254018=运算符不支持），抛 `BadRequestException`
- 未知错误继续抛出（保留 500 给真正的内部异常）

### 4. 前端兼容（PurchaseReqPage 读取侧）
- `safeItems` 或同等解析函数：若 items 为字符串则 `try JSON.parse`，失败返回 `[]`
- 提交侧不改（仍是数组），由服务端统一序列化

## 具体步骤
1. 读 `server/config/feishu.config.ts` 确认已有 TABLE_MAP/TABLE_KEYWORD_FIELDS 结构，在同区域新增 `JSON_TEXT_FIELDS`
2. 读 `server/common/feishu/field-normalizer.ts` 的 toBitableValue 与 normalizeRecord，在各自末尾加 JSON 文本字段双向转换
3. 读 `server/modules/bitable/bitable.entity.service.ts`，给 create/update/batchCreate/batchUpdate 四处加 try/catch + 错误码映射
4. 读采购申请页与表单组件，给读取侧 items 解析加字符串兼容
5. curl 自测：POST 一条含明细数组的采购申请，断言 200 且返回记录的采购明细为 JSON 字符串；再 GET 读回，断言解析为数组
6. 回归：客户/消耗等非 JSON 字段的创建/读取不受影响

## 影响范围与风险
- 影响：采购三表（申请/订单/详情）的明细字段写入格式从「对象数组」变为「JSON 字符串」；存量数据若已有其他格式（如纯文本），读取侧 try/catch 兼容
- 风险：Bitable 侧若采购明细实际是子表/关联表而非文本字段，JSON.stringify 反而会破坏结构 → 用 Bitable listFields API 或建一条测试记录验证字段类型后再定
- 不影响：财务资金联动（采购表不在联动 8 表内）、素材库、任务中心等其他模块

## 验收标准
- 新建采购申请（含≥1 条物品明细）→ 200，记录出现在列表中
- 编辑该申请 → 明细正确回显为可编辑行
- 删除该申请 → 列表移除（二次确认正常）
- 故意传非法字段（如数字字段传字符串）→ 返回明确中文错误（如「字段类型不匹配」），不再是裸 500
- 其他表（客户、消耗）的创建/读取回归正常

## 未决事项
- 采购明细在 Bitable 的实际字段类型需实测确认（文本 vs 子表）；若为子表则方案需改为创建主记录 + 批量创建子表记录（复杂度显著增加）。先用测试写入 + listFields 验证，按结果选择路径。
