# 牧唐数智一体化 · 全栈升级（数据存储迁移）方案

## 1. 目标与成功标准
- 应用在平台全栈模板下正常启动：NestJS 3000 端口（源码模式、devServer 托管、常驻），编译零错误，不再依赖旧 Express 3001 进程。
- 业务数据全部落到平台 Postgres（Drizzle schema），前端刷新后数据持久；用户打开预览（工作台 /customer/customers 等页）拿到与升级前一致的真实数据，不退回 mock。
- 验收硬数字（来自升级前已验证的多维表数据）：客户管理 30 条；dashboard range=month：yesterday_consume=517532.62、period_consume=3301648.05、customer_total=30、month_new_orders=24。
- 前后端基地址统一为同源 `/api`（vite dev-proxy → localhost:3000；生产 NestJS ViewModule 同源服务 dist/client），永久消除 3000/3001 不一致。

## 3. 实现方案
- **存储统一为平台 Postgres**：~70 张业务表（客户/广告/财务/审批/人资/行政/视频/合同/任务/系统）。主键 `bigserial`（兼容前端数字 id 语义与 SQLite 迁移零外键重映射）；每表带平台系统字段 `_created_at/_created_by/_updated_at/_updated_by`；RLS 按数据库 skill 规范给 authenticated 角色读写（登录用户内部 ERP）。中文表键（entity 路径 31 个，映射自 `server/config/index.ts:11-54` 的 29 张多维表）与 snake 表（直连路径 ~45 张）映射到同一批物理表，一个存储两个 API 门面，避免数据双份。
- **数据源**：29 张 entity 表（客户/广告/财务/审批）从飞书多维表迁移（已清理测试残留、是上一轮验证数字的来源）；其余从 `data/mutang-erp.db`（SQLite，76 张）迁移，迁移时过滤名称含 测试/test/CRUD/映射/权限 的残留记录。
- **数据通道**：脚本生成 DDL 与 INSERT SQL → `lark-cli apps +db-execute`（按 lark-apps-db skill 通道执行）→ `npm run gen:db-schema` 重新生成 schema.ts → 再写业务代码。
- **API 契约零变化**：保持旧 Express 的 URL、方法、请求/响应结构（`{code, message, data:{list,total,page,pageSize}}`、中文表键、record_id 即 id 字符串化、snake_case 直连键），前端 entities.ts / api/index.ts / dashboard-api.ts / auth.ts 全部不动。
- **前端仅改基地址**：`resolveBaseUrl()` 删除 localhost:3001 与端口前缀分支，恒返 `'/api'`；mock 兜底与四态降级逻辑保留不动（NestJS 未就绪阶段页面降级 mock 不白屏）。
- **鉴权**：登录沿用 admin/admin123（/api/auth/login 校验后签发 token）；写接口加 `@NeedLogin()`；`/api/auth/me` 优先取 `req.userContext` 平台身份映射。
- **旧 3001 进程**：执行阶段 `pkill -f "tsx server/index"`，确认 3000/3001 无残留冲突。

## 4. 具体步骤
1. **修启动失败**：把 `server/services/feishu-client.ts`、`server/db.ts` 等迁移要复用的模块复制进 `scripts/migrate/`；删除 server/ 下旧 Express 死代码（上列清单），devServer 重新编译通过、NestJS 3000 启动（此时无业务端点，前端降级 mock，页面不白屏）。
2. **建表与灌数据**：写 `scripts/migrate/` 脚本（tsx 运行）：读多维表 listFields/listRecords + SQLite 表结构/数据 → 生成 DDL（含系统字段与 RLS 策略）与参数化 INSERT → 经 `lark-cli apps +db-execute` 分批执行 → 抽查 count 对账（客户管理=30、消耗等各表计数）。跑 `npm run gen:db-schema` 重生成 schema.ts 并重新读取。
3. **NestJS 业务模块**：先补 `shared/api.interface.ts` 类型 → 主 agent 串行预填 `server/app.module.ts` → 实现 DataModule（entity 通用 CRUD + 通用 REST 工厂 + 特殊动作端点，特殊动作以 `grep "apiPost(\|apiGet(" client/src/api/index.ts` 的 223 个直连调用清单逐一核对覆盖）、DashboardModule（移植聚合，含 range=today/week/month/year 语义）、AuthModule（login/me/logout/users）。
4. **前端切换基地址**：`client/src/api/request.ts` resolveBaseUrl → `'/api'`，devServer 热更新生效。
5. **验证与提交**：api_request 逐类自测（entity list/create/update/delete、dashboard 各 range、auth login/me）→ 浏览器/E2E 按用户路径打开工作台与客户/广告/财务列表确认真实数据 → 四态防崩抽查（后端停/空表/报错时降 mock 不白屏）→ TS 检查与生产构建零错误 → commit。

## 5. 影响范围与风险
- 删除旧 Express 代码不影响平台关键文件（main.ts/app.module.ts 仅按模板约定追加 import）。
- 风险一：SQLite 与多维表数据不一致 → 以多维表为准（验收数字锚定多维表聚合）；对不上的表执行阶段对账后人工裁决。
- 风险二：~40 张直连表的特殊动作端点多（claim/approve/submit/confirm 等）→ 以前端 223 个调用清单为核对基线，逐一覆盖；漏掉的端点表现为 404，可用 api_request 扫描发现。
- 风险三：bigserial 主键与平台示例 uuid 风格不同 → 属于允许的业务选择（前端大量数字 id 语义），在 schema 注明。
- mock 兜底保留：NestJS 重启间隙或接口异常时页面仍可用（防崩四态），不视为"假数据冒充"——真实数据路径验收独立进行。

- 浏览器按用户预览路径（相对路径走 vite 入口）打开工作台与客户列表，显示真实数据非 mock 标识。
