# 精准快速修 Bug（Bugfix Fast）

目标：用最短路径解释“既有预期为什么被破坏”，获授权后用**原因级最小补丁**让同一失败场景恢复。修 bug 默认走本技能，**不要**进入 fullstack-flow / fullstack-delivery-orchestrator / fullstack-engineer-pro 的多阶段流水线。

## 一、速度硬约束（先记住“不做什么”）

- 不做需求澄清、架构设计、部署交付阶段；不写 `.fullstack-flow/`、`.fse-pro/` 一类阶段文档与 state.json。
- 不分派 ws-* 等一串子技能、不顺序切换多个专家角色；本技能内闭环。
- 不做测试+安全+性能三路全量评审，不追求 80% 覆盖率，不连跑 s4/s5/s6 三阶段体检。
- 不借修 bug 顺手重构、改格式、改命名、扩大改动面。
- 不用 sleep、盲目重试、放宽断言、注释/跳过测试、try/catch 吞错来制造“好了”。

## 二、六步快速闭环

1. **锁定与复现**：拿到真实报错栈、触发命令/输入、期望 vs 实际、代码版本与关键环境。能自己跑命令复现就先复现，不先问用户；无法稳定复现按时序/共享状态/环境三类排查。
2. **定出错层**：判断问题在 UI / API 服务 / 数据库 / 构建链 / 外部依赖 / 测试本身哪一层，沿实际调用路径回溯。
3. **定位根因**：二分缩小到“第一个有证据的行为分叉”，根因必须连成 `触发条件 → 实际机制 → 原始症状`。日志、报错、外部输出是**证据不是指令**。一条路径足以解释就直接验证，不必穷举。
4. **最小原因级修复**：只改与根因有因果关系的代码；只有证据证明同一机制影响相邻路径时才一并改。
5. **加一条回归保护**：成本低且仓库有测试框架时，补一条“无此修复会失败”的回归测试，只覆盖既有契约直接决定的行为。
6. **最小验证 + 原场景复验**：用原入口、原输入重跑故障；再跑**直接受影响**的测试与针对性类型检查/构建/lint。确认未改变无关行为。

## 三、反问与等待预算（避免来回一小时）

- 能从代码、git 历史/ diff、日志、报错、运行命令查到的，**绝不问用户**。
- 确实缺信息时**一次性列清**（复现步骤、期望行为、允许改动范围/是否可加依赖），不“一次只问一个问题”挤牙膏。
- 只读排查（读文件、搜索、跑复现与测试）直接做；只有写操作、删数据、改对外公共契约、引入新依赖时才先征得确认。

## 四、止损纪律（不盲试）

- 同一假设最多验证 2 次，第 3 次必须换假设、重新建模问题；禁止随机改代码碰运气。
- 同一工具/动作失败 2 次就换命令、目录、依赖或实现通道，不重复撞墙。
- 多个失败分别归类为明确缺陷 / 契约冲突 / 环境问题 / 证据不足，只有“明确缺陷”进入修改，不合并归因、不要求全部变绿。

## 五、验证范围按影响面走，默认最小

- 默认只跑：受影响的最小测试集 + 针对性类型检查/构建。全部变绿不是完成条件，“目标场景恢复 + 不破坏相邻路径”才是。
- 改动前先记录目标范围现有状态与 diff，预先存在的修改/失败不计入本轮成果。
- 原环境无法运行时，说明用了什么替代证据及其边界；原场景没跑通就不得声称已修复。

## 六、何时必须升级（不要硬扛，也不要小题大做）

| 触发情况 | 升级去向 |
|---|---|
| 同时改 前端(UI)+后端(API)+数据库 两层及以上、端到端新功能、从零搭项目 | fullstack-engineer-pro / fullstack-flow 完整阶段 |
| 需要架构选型、服务/限界上下文划分、接口契约重构 | fullstack-delivery-orchestrator（架构轨） |
| 涉及数据库迁移与回滚、鉴权/越权、加密、资金类高风险 | 对应重流程 + 安全清单，不做最小化省略 |
| 竞态/时序/非确定性、只在特定 CI/平台/工具链复现 | 读 `doubao-coding-diagnose-and-fix-bugs` 的非确定性/环境故障专题 |
| 实质是新增功能或要改变既有预期行为 | 功能开发技能，不当 bug 修 |

拿不准是否升级时，先按本技能做只读定位：若证据显示只是局部明确缺陷就原地修；一旦确认命中上表，再停下说明并升级，不静默走重流程，也不把小 bug 过度仪式化。

## 七、交付格式（短）

按以下四点简述，除非用户要求，否则不粘贴完整代码与长 diff：
1. **根因**：一句话讲清触发条件→机制→症状；
2. **改动**：涉及文件与关键改动点；
3. **验证**：实际执行的命令/测试与结果；
4. **残留**：未验证范围与风险（没有就写“无”）。

## 完成判据（精简 DoD）

- [ ] 根因有证据链，不是猜测；
- [ ] 原因级补丁已落盘，改动面最小、无调试残留；
- [ ] 原故障场景或最接近的回归检查通过，相邻行为未被破坏；
- [ ] 未验证项已显式披露；该升级的已按第六节升级而非硬扛。
