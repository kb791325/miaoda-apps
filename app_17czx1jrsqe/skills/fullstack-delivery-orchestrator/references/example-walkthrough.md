# 完整走查样例（Example Walkthrough）

> 用一个真实小项目演示六阶段怎么走、每阶段产出什么、质量门如何卡人。AI 执行本技能时对照此节奏，不跳步、不空喊"完成"。
> 案例：用户只说了一句——"帮我做个短链接服务，把长网址变成短码，访问短码能跳回去"。

## 0. 入口分诊
- Q1 坏了？否。Q2 新建？是 → 建设轨，从 S1 开始。
- 跨层（API+DB+跳转服务），判定为必须走完整六阶段，不允许直接写代码。

---

## S1 需求澄清（产出：需求规格，用户确认后才放行）

主动补齐用户没说的要素，列出需要确认的关键问题：
1. 短码长度/是否自定义？冲突怎么办？
2. 是否需要登录、过期时间、访问统计？
3. 预估 QPS 与数据量级？部署环境？
4. 重复长链接：每次生成新码还是返回旧码？

产出规格（节选）：
- FR-1 [When 提交合法长 URL] 系统必须生成全局唯一短码并存储映射，返回短链。
- FR-2 [When 访问短码] 系统必须 302 跳转到原 URL；短码不存在返回 404 页面。
- FR-3 [If URL 非法/不可达/为内网地址] 系统必须拒绝并说明原因（防 SSRF）。
- FR-4 [While 并发生成] 系统必须不产生重复短码。
- FR-5 [Ubiquitous] 系统必须记录每次跳转的时间、短码（统计用），异步落库不阻塞跳转。
- 验收：AC-1 合法 URL 返回长度 7 的短码且可跳转；AC-2 错误 URL 返回 422；AC-3 100 并发生成无重复；AC-4 跳转 p95 < 50ms（缓存命中）。
- 范围：本期不做账号体系、自定义短码、管理后台（记入"不做"）。
- 假设（用户未答时显式标注）：短码 Base62 长度 7；默认永不过期；单机 PG + 内存缓存起步。

**S1 门**：每条 FR 可测、范围明确、关键问题已确认 → 用户确认，放行。

## S2 架构设计（产出：架构图/模型/契约/ADR/NFR）

- 组件视图（文字 C4）：`Client → Nginx → shortlink-service(Spring Boot) → PostgreSQL；跳转热点走 Caffeine 本地缓存；访问事件经内存队列异步批量写 analytics 表`。
- 数据模型：
  - `link(id BIGINT 主键, short_code varchar(12) 唯一索引, long_url text, created_at, expire_at NULL)`
  - `click_event(id, short_code, clicked_at, referer)` 只追加；按天分区预留。
- 接口契约：
  - `POST /api/links {url}` → 201 `{shortUrl, shortCode}`；422 错误结构 `{code,message,details}`
  - `GET /{code}` → 302 Location: long_url；404
- ADR：
  - ADR-001 短码生成用"发号器+Base62"而非随机撞库（避免并发查重、保证不重复，对应 FR-4）。
  - ADR-002 跳转读缓存、写事件异步（对应 AC-4 性能；代价是统计有秒级延迟，可接受）。
  - ADR-003 先做 URL 白/黑名单校验与私网地址拦截（防 SSRF 安全基线）。
- NFR：跳转 p95<50ms；生成接口 <200ms；可用性单实例；日志带 traceId。

**S2 门**：每个 FR 都能在模型/接口中找到落点（无孤儿需求）；取舍有 ADR；用户确认技术栈 → 放行。

## S3 计划拆解（产出：纵向薄片任务单）

| ID | 任务 | 关联 | 完成判据 |
|---|---|---|---|
| T1 | 迁移脚本：link/click_event 表与索引 | FR-1 | 空库可升、可回滚 |
| T2 | 发号器+Base62+短码生成服务（单测含并发生成） | FR-1/4 | AC-3 并发测试通过 |
| T3 | 创建短链接口+URL 校验（SSRF 防护） | FR-1/3 | AC-1/AC-2 |
| T4 | 跳转接口+缓存+异步事件 | FR-2/5 | AC-4，事件不丢（测试） |
| T5 | 404 页与全局异常/错误码 | FR-2 | 异常路径测试齐 |
关键路径 T1→T2→T3→T4，T5 与 T4 并行。每片都可演示。

**S3 门**：无大而糊任务、每任务有判据、用户确认先做 T1-T5 → 放行。

## S4 编码实现（逐任务：先测试后实现，每层即时验证）

以 T2 为例的节奏：
1. 先写测试：Base62 编码正确性、发号不重复、100 线程并发取号断言唯一。
2. 实现：号段用数据库序列/号段模式，Base62 定长编码，补零与字典序防猜测。
3. 即时验证：`mvn -Dtest=CodeGeneratorTest test` 绿，再进下一任务。
关键实现纪律（对照 stack-playbooks）：
- controller 只校验/转发；业务在 service；事务只包住"取号+写映射"。
- URL 校验：协议白名单(http/https)、域名解析后拒绝私网/环回/链路本地地址（防 SSRF），禁止仅靠前端校验。
- 缓存：Caffeine 容量与过期显式配置；缓存未命中回源后回填；事件队列有界、拒绝策略显式声明，不允许默认无界队列 OOM。
- 配置：短码长度、缓存容量走 application.yml + 环境变量；提供 .env/example 说明。

**门回退示范**：T4 实现时发现 S2 没定义"短码过期/失效"语义，而 link 表有 expire_at 字段——回到 S2 补一条 ADR-004（过期判定在跳转时、过期返回 410），同步更新 FR 与 T4 判据，再继续。门不过就回退，而不是带着歧义硬写。

**S4 门（逐任务）**：编译通过、任务相关测试绿、无 skip/吞异常/硬编码密钥、分层与 S2 一致。

## S5 质量保障（产出：测试结果+评审闭环）

1. `mvn clean verify`：单测 + 集成测试（Testcontainers 起真实 PG）全绿。
2. java-spring-boot-verification-loop：静态分析（SpotBugs/CheckStyle）、依赖漏洞扫描、diff 自审。
3. 五维评审发现并闭环（示例）：
   - 正确性：异步事件队列满时会丢数据 → 改有界队列+降级写日志补偿，补测试。
   - 安全：原 URL 校验可被 DNS rebinding 绕过 → 解析后用解析到的 IP 发起请求、禁私网；补用例。
   - 性能：跳转每次查库 → 缓存命中后 p95 达标；补一个缓存命中基准。
   - 可维护：魔法数字散落 → 收敛配置类。
   - 测试：缺 410/404/并发三条路径 → 补齐。
4. 运行 `scripts/preflight_check.py . --stage s5`，BLOCKER 清零。

**S5 门**：构建/测试/静态检查全绿（留存输出）；评审问题全部 closed；安全清单逐条过 → 放行。

## S6 交付验证（产出：真实入口验证+交付说明）

1. 不同于写代码的路径验证：真实 `java -jar` 启动 → curl 创建短链 → 浏览器访问短码看 302/跳转/404/410；并发脚本压 100 次创建验唯一。
2. verifier-hub 校验产物（jar/迁移脚本/文档）可打开、结构正确；artifact-preview 看 404 页面渲染。
3. 交付说明（对照模板 D）：
   - 产物：shortlink-service 源码与 jar、迁移脚本、README（启动步骤/配置项/curl 示例/回滚方式）。
   - 验证记录：构建 48 测试全绿、并发无重复、跳转 p95 38ms、SSRF 用例拦截正确。
   - 覆盖 FR-1~5/AC-1~4；残留风险：单机部署无高可用、统计延迟秒级（已在 ADR 记录）；后续建议：号段预取优化、管理后台。

**S6 门**：真实主流程跑通、用户可直接运行、验证方式与缺口写清 → 交付完成。

## 走查要点总结（AI 自查）
1. 用户一句话需求，没有直接写代码——S1 先问清并写规格。
2. 每个阶段都有落地产物，下一阶段能引用上一阶段的编号（FR/ADR/任务 ID 全程可追溯）。
3. 发现歧义（过期语义）时回退补设计，而不是带着问题冲。
4. 测试先于/同步于实现；安全（SSRF）、性能（缓存）、并发（发号器）在 S2 就有方案，不是 S6 救火。
5. 交付靠真实运行证据，不靠"代码写完了"的口头声明。
