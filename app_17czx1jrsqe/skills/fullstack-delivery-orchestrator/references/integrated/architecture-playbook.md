# 03 · 架构设计手册（跨语言）

> 对应主线 C，也在主线 A 的 A2 使用。先选架构形态，再定契约与一致性，最后落 ADR。语言相关实现（注解、代码）查 04/05/06。

## 1. 三种主流后端架构形态（按项目复杂度选，brownfield 沿用既有形态）

### 1.1 分层架构（默认，绝大多数 CRUD/业务系统）
```
Controller/路由   只做协议转换：解析请求、@Valid/入参校验、返回响应；每端点只调一个服务方法
      ↓ DTO/命令对象
Service/用例层    全部业务逻辑与编排；事务边界在这一层；一个聚合根一个服务
      ↓ 领域对象/实体
Repository/DAO   只做数据访问，无业务逻辑，返回实体或投影
      ↓ ORM/驱动
Database
```
铁律：控制器不写业务、不直接访问 DAO、不直接返回持久化实体；Service 不出现 HTTP 类型；配置类只装配基础设施、不依赖 Service。

### 1.2 六边形 / 端口-适配器（复杂领域、要可测试、要隔离框架）
```
domain/            纯领域模型 + port/in（用例接口，驱动端口）+ port/out（仓储/外部接口，被驱动端口）
application/       用例实现，编排领域与端口（这里才允许出现框架注解、事务）
infrastructure/    persistence(JPA/ORM 适配器实现 out 端口)、web(控制器驱动适配器)、external(HTTP/消息适配器)
```
铁律：**domain 零框架依赖**（不出现 `javax/jakarta.persistence`、不注入 ORM Repository、不放 `@Transactional`）；用例依赖的是领域端口接口而非具体 ORM；区分驱动端口 in 与被驱动端口 out；领域对象带行为，不写只有 getter/setter 的贫血模型。

### 1.3 DDD（领域复杂、多聚合协作时叠加在 1.1/1.2 上）
- **聚合**：以聚合根为一致性边界，外部只持有聚合根引用与其 ID；一个事务只修改一个聚合实例，跨聚合用最终一致。
- **值对象**：不可变、以属性判等（如 `OrderId(UUID)`、`Money`），用 record/不可变类表达。
- **领域事件**：聚合内收集事件，提交成功后再发布（见 §4 AFTER_COMMIT）。
- **规约（Specification）**：复杂查询用可组合规约对象表达，而不是散落的 if/SQL 拼接。
- **防腐层 ACL**：对接遗留/外部系统时用适配器把外部模型翻译成自己的领域模型，不让外部概念污染领域。

### 选型建议
简单业务 → 分层；领域复杂且要长期演进/多通道（HTTP+消息+定时任务）→ 六边形；跨团队、多子系统 → 六边形 + DDD + 微服务。不要为简单 CRUD 上六边形增加无谓层数。

## 2. API 契约优先
### 2.1 统一响应信封（团队选定后全项目一致）
成功：`{ "success": true, "data": {...}, "error": null, "timestamp": "..." }`；
失败：`{ "success": false, "data": null, "error": {"code":"ORDER_NOT_FOUND","message":"...","details":[]}, "timestamp":"..." }`。
对外 REST 也可用 RFC 9457（Problem Details）表达错误；二选一，不混用。
### 2.2 HTTP 状态码映射
| 场景 | 码 | 场景 | 码 |
|---|---|---|---|
| GET 成功 | 200 | 校验失败 | 400 |
| POST 创建 | 201 | 未认证 | 401 |
| PUT/PATCH 更新 | 200 | 无权限 | 403 |
| DELETE | 204 | 不存在 | 404 |
| 冲突/重复 | 409 | 未处理异常 | 500 |
### 2.3 URL 与分页
- 资源用复数名词、多词 kebab-case：`/api/v1/orders`、`/order-items`；版本放路径；嵌套最多 2 层，更深就拍平。
- 对外 ID 优先 UUID，不暴露自增整数。
- 列表必须分页，且**强制页大小上限**（裸分页可能被 `?size=100000` 一次拖全表进内存；Spring 设 `spring.data.web.pageable.max-page-size`，其他框架同理在入口 clamp）。
- 全局异常处理集中到一处（如 `@RestControllerAdvice` / 统一错误中间件），控制器内不 try/catch 兜底；500 不回传内部堆栈。
### 2.4 契约与版本
接口先定请求/响应 schema 与错误码再写实现（spec-driven）；需要多方协作时 OpenAPI-first，契约即文档与测试桩；破坏性变更走新版本，不悄悄改字段。

## 3. 数据一致性与事务
### 3.1 事务边界
- 事务注解/事务块放在**服务/用例层的公开方法**上，不放控制器或仓储；私有方法、自调用会让基于代理的声明式事务失效（Spring 尤其注意，需拆到独立 Bean 或注入自身）。
- 只读方法标只读（如 `@Transactional(readOnly=true)`）以启用驱动优化；类级默认只读、写方法单独覆盖。
- 默认传播 `REQUIRED`（加入已有事务否则新建）；需要"主事务回滚但审计仍落库"用独立新事务（`REQUIRES_NEW`）。
- 默认只对运行时异常回滚；受检异常要回滚需显式声明 `rollbackFor`。
- 乐观并发用版本号（`@Version`）而非先锁；冲突抛专门异常由上层决定重试还是报错。
### 3.2 跨服务/跨聚合一致性：Saga，不要分布式强事务
编排式或协同式 Saga：每步都配**补偿动作**，任一步失败按逆序补偿；写操作必须幂等（幂等键），因为补偿/重试会重复到达。
### 3.3 事务内禁止外部副作用
发邮件、发 Kafka、调 webhook、预热缓存**不能放在事务提交前**——事务一旦回滚，消息已经发出去了。正确做法：事务内只登记事件，提交成功后再触发（`@TransactionalEventListener(AFTER_COMMIT)` / outbox 模式 / 事务提交后回调）；监听逻辑若要写库需开新事务。

## 4. 微服务架构（确实需要时才拆，单体优先）
拆分前提：团队边界清晰、可独立部署、能接受最终一致。要素：
- **服务发现/注册**（Eureka/Nacos/Consul）；**API 网关**统一路由、鉴权、限流（Spring Cloud Gateway 注意与 Boot 版本兼容矩阵）。
- **韧性四件套**：超时（必设，默认 2s 量级按业务定）、重试（仅对幂等读、指数退避、`maxAttempts` 含首次调用）、熔断（失败率阈值后快速失败 + fallback 缓存/降级）、限流/舱壁隔离。
- **分布式配置**：配置中心 + 环境隔离 + 敏感配置走密钥管理不入库。
- **服务间通信**：同步（HTTP 声明式客户端，带超时/熔断）与异步（消息，事件契约向后兼容、消费者幂等、死信队列）。
- **可观测**：统一 traceId 贯穿调用链、结构化日志、RED 指标（Rate/Error/Duration）、健康/就绪探针。
- 反模式：为拆而拆、分布式单体、同步调用环、共享数据库、无超时的级联调用。

## 5. 架构评审检查单
- [ ] 分层/端口边界是否被穿透（控制器业务、领域依赖框架、跨层访问 DAO）？
- [ ] 每个接口契约（入参/出参/错误码/权限）是否明确且与实现一致？
- [ ] 事务边界是否在正确层、是否存在自调用失效、事务内外部副作用？
- [ ] 跨服务一致性是否用 Saga+补偿+幂等，而非分布式事务/侥幸？
- [ ] N+1、深分页、缺索引、无界列表等数据访问风险（详见语言手册）？
- [ ] 鉴权授权是否到数据级（水平/垂直越权），而不仅是"登录了没"？
- [ ] 外部依赖是否都有超时、重试边界、熔断/降级？
- [ ] 是否记录了 ADR：背景、候选方案与取舍、决定、后果与风险？
