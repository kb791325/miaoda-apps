# 阶段质量门与模板（Stage Gates）

> 每阶段 = 进入条件 → 必做动作 → 产出物 → 退出检查清单（全部勾选才放行）。
> 门不过：回到本阶段补齐；连续两次无法满足，向用户说明阻塞与所需输入，不假装通过。

## 目录
- S1 需求澄清门
- S2 架构设计门
- S3 计划拆解门
- S4 编码实现门
- S5 质量保障门
- S6 交付验证门
- 模板 A：需求规格说明
- 模板 B：架构决策记录 ADR
- 模板 C：实施计划任务单
- 模板 D：交付验收单
- 附：填写样例

---

## S1 需求澄清门

进入条件：用户有新建/改造意图（哪怕只有一句话）。

必做动作：
1. 识别角色、核心业务流程、输入输出、数据归属、部署环境、约束与禁区。
2. 每条功能需求写成 EARS 句式并配验收标准。
3. 列出未决问题；会改变架构的关键歧义一次性向用户确认，其余自行假设并标注。

退出清单：
- [ ] 范围写明"做什么/不做什么"
- [ ] 每条需求可通过给定输入验证对错
- [ ] 非功能需求（性能/并发/安全/兼容）已明确或显式标注待定
- [ ] 用户已确认需求规格（或已给出默认假设并获默认放行）

## S2 架构设计门

进入条件：S1 清单全过。

必做动作：
1. 画上下文图/容器图/组件图（ws-c4-architect），标清数据流。
2. 定数据模型（实体、关系、关键字段、索引）与接口契约（路径、方法、入参出参、错误码）。
3. 每个有取舍的决策写 ADR；微服务场景给出限界上下文边界与通信方式。
4. 过一遍 NFR：可用性、性能量级、安全边界、可观测、扩展方式。

退出清单：
- [ ] 架构图覆盖所有 S1 需求，无"孤儿需求"
- [ ] 数据模型与接口契约互相一致，命名统一
- [ ] 关键技术选型均有 ADR，且与用户点名技术栈不冲突
- [ ] 标出最高风险的 3 个点及应对

## S3 计划拆解门

进入条件：S2 清单全过。

必做动作：
1. 按可独立演示的纵向薄片切任务；每任务绑定需求编号。
2. 标依赖关系、关键路径、每任务完成判据与验证命令。
3. 需要协作时把任务写入 lark-task / lark-project。

退出清单：
- [ ] 无超过 1 天工作量或跨 3 个以上模块的"大任务块"（有则继续拆）
- [ ] 每任务都有可执行的完成判据
- [ ] 集成顺序明确，先打通主干再补分支
- [ ] 用户确认首个迭代范围

## S4 编码实现门

进入条件：S3 清单全过、开工范围确认。

必做动作（每个任务循环）：
1. 先写/补该任务的测试用例（test-driven-development），再实现。
2. 分层落地：实体/迁移 → 数据访问 → 业务逻辑 → 接口 → UI，每层完成立即跑最小验证。
3. 错误处理、参数校验、日志、配置外置与功能同批完成。
4. 提交前本地跑通：编译/构建 + 该模块测试 + lint/类型检查；并跑 `scripts/preflight_check.py <根> --stage s4`。

退出清单（逐任务）：
- [ ] 代码可运行（启动/构建命令实际执行通过，附结果）
- [ ] 对应单元测试已写且通过，不新增 skip
- [ ] 无吞异常、无硬编码密钥、无被注释掉的失败测试
- [ ] 与 S2 分层一致；偏差已回写 ADR/设计说明

## S5 质量保障门

进入条件：计划内功能代码完成。

必做动作：
1. 全量构建 + 测试套件 + 静态检查；Java 走 java-spring-boot-verification-loop。
2. 跑 `scripts/preflight_check.py <根> --stage s5`，BLOCKER 清零。
3. 代码评审五维：正确性、安全（注入/XSS/越权/密钥）、性能（N+1/全表扫描）、可维护性、测试覆盖。
4. 安全清单：鉴权、输入校验、输出编码、参数化查询、依赖漏洞、最小权限。
5. 问题建清单逐条闭环，记录修复方式与回归结果。

退出清单：
- [ ] 构建/测试/静态检查全绿（截图或输出为证）
- [ ] preflight 静态体检 0 BLOCKER
- [ ] 评审问题全部 closed；遗留项有风险接受记录
- [ ] 关键路径有集成/E2E 覆盖
- [ ] 已知边界与失败模式写入说明

## S6 交付验证门

进入条件：S5 清单全过。

必做动作：
1. 用不同于"写代码"的路径验证：真实启动服务/打开页面/走完整用户流程（verification-before-completion、artifact-preview）。
2. 跑 `scripts/preflight_check.py <根> --stage s6`（含 README/.env.example 齐备性检查）。
3. 用 verifier-hub 对产物做确定性校验（格式/结构/可打开）。
4. 写运行说明：启动步骤、环境变量、示例请求、回滚方式。
5. 交付物经 present_files/在线链接交付，说明已验证范围与残留缺口。

退出清单：
- [ ] 真实用户入口端到端跑通至少一条主流程
- [ ] 产物可被用户直接打开/获取
- [ ] 数字与外部事实有来源；计算可复现
- [ ] 交付说明含：验证方式、覆盖范围、未覆盖风险、后续建议

## 附：填写样例（以"库存管理-入库登记"功能为例）

### 样例 A：需求规格（节选）
```
# 需求规格：库存入库登记
## 1. 背景与目标
- 业务背景：仓管目前用微信群报入库，台账滞后、经常超卖。
- 成功指标：入库后台账 5 秒内可查；库存数量零负库存。
## 2. 角色与场景
| 角色 | 场景 | 期望结果 |
| 仓管员 | 采购到货后登记入库批次 | 生成入库单并增加库存 |
| 主管 | 查看当日入库汇总 | 看到按 SKU 汇总的数量与金额 |
## 3. 功能需求（EARS）
- FR-1 [When 仓管员提交合格入库单] 系统必须生成唯一入库单号并按批次增加对应 SKU 库存。
- FR-2 [If 提交数量 ≤ 0 或必填批次缺失] 系统必须拒绝并逐字段提示。
- FR-3 [While 同一 SKU 存在未完成入库单] 系统必须串行化库存变更，禁止出现负库存。
- FR-4 [Ubiquitous] 系统必须记录每次库存变动的操作人、时间、来源单据。
## 4. 验收标准
- AC-1 Given 一张数量10、SKU=A01的合格入库单 When 提交 Then 库存A01增加10且生成状态为"已入库"的单据。
- AC-2 Given 数量为-1 When 提交 Then 返回422且库存不变。
- AC-3 Given 两个并发入库同一SKU When 都完成 Then 最终库存=两次数量之和（无丢失更新）。
## 6. 范围边界
- 本次做：入库登记、库存台账、变动流水、当日汇总。
- 本次不做：采购对账、供应商门户、出库（下一迭代）。
## 7. 假设：单仓；并发 < 50 TPS；删除入库单用红冲而非物理删除。
```

### 样例 B：ADR（一条）
```
# ADR-003：库存并发控制选悲观锁行锁而非应用层分布式锁
- 状态：已接受
## 背景
同一 SKU 并发入库/出库会丢失更新（AC-3）。数据库为 PostgreSQL，TPS 不高。
## 候选
1. 应用层 Redis 分布式锁：跨库通用，但引入新组件，锁泄漏/超时要处理。
2. DB 事务内 SELECT ... FOR UPDATE 行锁：实现简单、强一致，缺点是锁等待，高并发下吞吐下降。
3. 乐观锁版本号：无阻塞，但重试逻辑复杂，仓管场景冲突率低但要求一次成功。
## 决策
选 2。并发量 <50 TPS、单库，行锁足够且语义最直接；在 service 层事务内对 SKU 行加锁后计算。
## 后果
- 正面：无额外中间件；不会负库存、不丢更新。
- 代价：热点 SKU 会排队；缓解：事务只包库存计算、不包外部调用，设 3s 锁超时并友好提示。
```

### 样例 C：计划任务单（节选）

```
# 迭代1计划（纵向薄片）
| 任务ID | 任务 | 关联 | 改动面 | 依赖 | 完成判据 | 风险 |

```
